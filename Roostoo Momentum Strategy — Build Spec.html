Cross-Sectional Momentum Strategy — Roostoo Hackathon Build Spec

Purpose of this document: feed this to an AI coding assistant (Claude Code, Cursor, etc.) as the spec for an autonomous trading bot to build and deploy against the Roostoo mock exchange (https://mock-api.roostoo.com) for the HK vs AU vs IN Quant Trading Hackathon.

1. Problem framing

  • Screen 1 (mandatory): every trade must come from the bot's own autonomous loop — no manual API calls, clean and traceable commit history.
  • Screen 2: top 20 per region by raw portfolio return advance. The strategy cannot be overly conservative.
  • Screen 3: composite score = 0.4 × Sortino + 0.3 × Sharpe + 0.3 × Calmar. Drawdown control is worth more than raw Sharpe.
  • Screen 4: clean, well-structured repo that runs continuously and is compatible with Roostoo.
  • Spot only, 1x long and short permitted (no leverage), $100,000 mock USD portfolio.
  • Fees: 0.1% taker (market), 0.05%–0.1% maker/short depending on endpoint (see §5).
  • No HFT, market-making, or arbitrage. Bot must trade autonomously, at least 8 active days with a meaningful number of trades per active day.

Given this, the strategy needs to: (a) generate genuine positive expected return net of fees, (b) actively manage drawdown since it's 60–70% of the risk-adjusted score, and (c) trade often enough to satisfy the activity requirement without over-trading into fee drag.

2. Strategy: cross-sectional momentum with a trend filter and volatility-scaled sizing

Core idea: rank all tradable coins by recent risk-adjusted return, go long the strongest, short (or avoid) the weakest, filter everything through a market-regime trend check, and size positions by volatility with a hard drawdown circuit breaker.

2.1 Universe

Do not hardcode a pair list — pull it live from GET /v3/exchangeInfo, filter to pairs where CanTrade == true. From the API docs and examples, Roostoo's mock exchange has historically listed pairs like BTC/USD, ETH/USD, BNB/USD, ETC/USD, EOS/USD, TRX/USD, BAT/USD, LINK/USD and similar large/mid-cap coins — but the live, authoritative list only comes from exchangeInfo at runtime, since it can change. The bot should:

  1. Call exchangeInfo on startup and on a daily refresh.
  2. Build the tradable universe dynamically from that response.
  3. Optionally apply a liquidity filter using CoinTradeValue/UnitTradeValue from /v3/ticker, excluding illiquid pairs where slippage risk is high.

This makes the bot robust to whatever pairs are actually listed for the competition, and is safer than betting on a specific static list of "equities" (Roostoo only lists crypto/USD pairs, not equities).

2.2 Signal — momentum score per pair

For each pair i in the universe, on each rebalance:

ret_k(i)     = % return over lookback k (e.g. k = 6h, 24h, 72h)
vol(i)       = realized volatility of returns over a matching window (e.g. stdev of hourly returns, 7-day window)
mom_score(i) = weighted_avg(ret_6h, ret_24h, ret_72h) / vol(i)

Blending three lookbacks smooths out noise from any single window. Dividing by volatility (a simple risk-adjusted momentum score) prevents the ranking from being dominated by the single most volatile coin, which is a common failure mode of naive momentum.

2.3 Regime filter (market-wide)

Compute a trend filter on BTC (or an equal-weighted basket of the top few coins by trade value) — e.g. price above its 50-period moving average on hourly bars.

  • Risk-on regime: BTC trend is up → allow full long exposure, and shorts only on the very weakest names.
  • Risk-off regime: BTC trend is down → cut gross long exposure (e.g. to 30–50% of normal), and allow more short exposure on the weakest-ranked names.

This single filter is what should meaningfully help Calmar/Sortino, since crypto pairs are highly correlated and most drawdowns are market-wide, not pair-specific.

2.4 Long/short construction

Given the momentum scores and the regime filter:

  • Rank all pairs by mom_score.
  • Long book: top N pairs (e.g. N = 3–5) with a positive momentum score.
  • Short book: bottom N pairs with a negative momentum score, sized smaller than the long book by default (shorts have capped upside and real tail risk since a short can only be closed at market/limit — see §5), and only activated once you've confirmed the competition allows shorting (see below).
  • Cash: anything not deployed sits in USD. In a risk-off regime, cash allocation should rise.

Important operational check: the API docs explicitly list "this competition does not allow short positions" as a possible ErrMsg from /v6/short_open. Before relying on shorting at all:

  1. Try a tiny test short (e.g. $1–2 collateral) early, read the response.
  2. If shorting is disabled for this competition, the bot must gracefully fall back to a long/cash-only version of the same strategy (skip the short book, put that risk budget into deeper cash allocation during risk-off regimes instead).
  3. Build this as a config flag (SHORTING_ENABLED) so one bad API response doesn't crash the loop — catch Success: false and branch, don't assume it will always succeed.

2.5 Position sizing

  • Target volatility parity across positions: weight each position inversely to its recent volatility, then normalize so the book's total gross exposure hits a target (e.g. 80–100% of equity in a risk-on regime, lower in risk-off).
  • Cap any single position at, say, 20–25% of equity, so one coin can't dominate the book.
  • Circuit breaker: track running portfolio value and its peak. If drawdown from peak exceeds a threshold (e.g. 8–10%), cut gross exposure by half (or to cash) until the portfolio recovers a set amount from the trough. This directly targets Calmar.

2.6 Rebalance cadence

  • Rebalance every 4–12 hours (not tick-by-tick — this is explicitly disallowed as HFT-adjacent and burns fees).
  • Use a hysteresis band: only replace a held position with a new candidate if the new candidate's momentum score beats the held one by a meaningful margin (e.g. 20%+ relative), to avoid needless churn/fees on marginal rank flips.
  • This cadence, combined with $100k capital split across ~5–8 positions, should comfortably clear "enough trades per active day" without approaching HFT territory.

3. Why this design fits the scoring function

Screen How this strategy addresses it
Rule compliance Fully rule-driven, deterministic given market data — no manual intervention, clean logs of every decision and API call
Portfolio return Momentum + being invested in top-ranked names by default keeps the strategy return-seeking, not just defensive
Sortino / Sharpe / Calmar Vol-scaled sizing, regime filter, and drawdown circuit breaker are all specifically aimed at limiting downside vol and max drawdown
Code review Clean separation of signal / sizing / execution / risk modules (see §6) makes the strategy easy to explain and audit

4. Backtesting plan

  1. Pull historical OHLCV for the same pairs from a public source (the hackathon's Data Sources Pack, or a public exchange API like Binance for the same symbols, since Roostoo's own history is limited to what you log going forward).
  2. Build a vectorized backtester (pandas) that:
    • Computes signals with no lookahead (signal on bar t, trade executes on bar t+1).
    • Applies fees on every simulated trade (0.1% market / lower for resting limit orders) and slippage.
    • Enforces the same position caps, regime filter, and drawdown breaker as the live bot.
  3. Report the same three metrics the judges use — Sharpe, Sortino, Calmar — plus max drawdown and turnover, so you can sanity-check before deploying.
  4. Stress-test: double the assumed fees, and re-run with a couple of different lookback windows to confirm the strategy isn't overfit to one parameter set.

5. Roostoo API mechanics the bot must respect

  • Auth: RCL_TopLevelCheck endpoints need RST-API-KEY + MSG-SIGNATURE (HMAC-SHA256 of the sorted, &-joined param string, keyed by your secret) in the headers, plus a millisecond timestamp within 60s of server time.
  • Always check Success in the response body — failed requests still return HTTP 200.
  • Long/flat trading: POST /v3/place_order (MARKET or LIMIT, BUY/SELL). Respect each pair's PricePrecision, AmountPrecision, and MiniOrder from exchangeInfo, or orders are rejected.
  • Shorting: POST /v6/short_open (sized by collateral, not quantity) and POST /v6/short_close (by close_qty or close_pct). Check /v6/short_positions for live PnL. Handle the "this competition does not allow short positions" error as described in §2.4.
  • Order tracking: use /v3/pending_count and /v3/query_order to reconcile intended vs. actual state — don't assume an order filled just because you sent it.
  • Rate limits: "excessive server requests" cause failed responses — poll on a fixed schedule (e.g. once per rebalance cycle plus periodic balance/position checks), not in a tight loop.

6. Suggested repo / module structure

/bot
  config.py        # universe refresh interval, lookbacks, caps, drawdown thresholds, SHORTING_ENABLED
  roostoo_client.py# thin wrapper: signed requests, retries, Success-flag checking
  data.py          # ticker polling, local price history buffer, persistence
  signals.py       # momentum score, regime filter
  risk.py          # vol-scaled sizing, position caps, drawdown circuit breaker
  execution.py      # translate target weights -> orders, respect precision/MiniOrder, place/cancel
  state.py         # persist positions/equity curve/peak so restarts don't lose state
  main.py          # scheduling loop (e.g. APScheduler or a simple sleep loop under systemd)
  backtest.py      # offline backtester reusing signals.py and risk.py
logs/              # structured logs of every signal, decision, and order response
README.md          # strategy explanation, how to run, how to deploy on the AWS EC2 box

Keep signals.py and risk.py pure functions with no API calls — this is what lets you reuse them in backtest.py and makes the strategy logic auditable for Screen 4.
